# Python_TextFinder — Project Structure

The Python_TextFinder project comprises three libraries and one binary, arranged as four importable packages under one folder. The binary imports all three. The libraries themselves form a chain: `python_textfinder_dirnav` imports `python_textfinder_cmdline` for the program-command type, and `python_textfinder_output` imports `python_textfinder_dirnav` for the `Output` protocol. Nothing imports `python_textfinder_output` but the binary.

These specifications were written with the C# implementation in view, at the user's request, per [Constitution.md](../Constitution.md) rule 1. [Spec_TextFinder.md](../Spec_TextFinder.md) remains the authority: where a sibling and the project specification disagree, the specification wins, and every decision recorded below is taken from the specification rather than from what the sibling did.

## Libraries

- **python_textfinder_cmdline** — parses the command line into a `ProgramCommands` object whose attributes control the behavior of `python_textfinder_dirnav`. Python has free functions, so the parse entry, the usage line, the help text, and the option listing are module-level functions rather than static methods of a class: a class holding only static methods is a namespace, and a module already is one. Specified in [Spec_Python_TextFinder_Cmdline.md](Python_Spec_driven_Cmdline/Spec_Python_TextFinder_Cmdline.md).
- **python_textfinder_dirnav** — directory navigation. Reads file contents, runs regex matching, and formats each matching file into the block Spec_TextFinder.md §3.4 fixes before emitting its lines. Compiles the regular expression once per run, not once per file. Defines the protocol:
  ```python
  class Output(Protocol):
      def output(self, text: str) -> None: ...
  ```
  `Dirnav` binds to a concrete implementation through an annotated constructor parameter. Specified in [Spec_Python_TextFinder_Dirnav.md](Python_Spec_driven_Dirnav/Spec_Python_TextFinder_Dirnav.md).
- **python_textfinder_output** — implements `Output.output` according to its specification, [Spec_Python_TextFinder_Output.md](Python_Spec_driven_Output/Spec_Python_TextFinder_Output.md). Handles output errors internally.

Each library's package name matches its component name above, lower-cased with underscores, as Python names a package. The types inside carry their own names rather than the package's: the sink is `StdoutSink` in `python_textfinder_output`, so that `from python_textfinder_output import StdoutSink` reads as a type being imported from a place rather than a name being imported from itself.

## Binary

- **python_textfinder_entry** — binary package name; produces the executable `Python_TextFinder` through the launcher scripts described under Build. Imports the three libraries above. Specified in [Spec_Python_TextFinder_Entry.md](Python_Spec_driven_TextFinder_Entry/Spec_Python_TextFinder_Entry.md).
- Owns the skip list and passes it to `python_textfinder_dirnav` for use during traversal.
- On execution, `main(argv)` parses the command line into a `ProgramCommands` object using `python_textfinder_cmdline`.
- A `StdoutSink` is created and passed to a `Dirnav` as its output.
- The `Dirnav` object is started at each of the specified (possibly default) root paths in turn and performs a DFS for regex matches on files in each directory tree.
- Owns the process's one output object, which in turn owns the only writer over standard output. Every write to standard output, the binary's own help text and option listing included, passes through that object, so nothing else can interleave with the search output or reorder it.
- Holds that object in a `with` statement, so it is flushed on every path out of `main`.

## Build

- Language: Python. Interpreter minimum: CPython 3.10. Build system: none — Python compiles on import, so this implementation has no build step and no build definition. These apply to every package below, and each component's `Spec_*.md` names only its own package.
- Four packages under one folder, one per component, each in its own component folder under `src/`. Each library is a separate package rather than a module of one package, so the dependency chain above is visible as an import graph. Python enforces no such chain: any package on `sys.path` may import any other, and the chain is a rule these specifications state rather than one a tool holds. That is a stated difference from the C++, Rust, and C# implementations, where the build refuses a dependency the structure does not declare.
- Each component has its own folder holding its `Spec_*.md`, its package under `src/`, and — for the three libraries — its unit suite under `test/`, which Spec_TextFinder.md §6.2 asks to live beside the code it tests. The integration suite and the demonstration drive the assembled program, so both sit at the root of this folder rather than in a component folder, as do the three runners and the two launchers.
- Imports resolve through `PYTHONPATH`, which carries the four `src/` folders. The launchers and the runners set it; a reader invoking the interpreter directly sets it too. An editable install through `pip` is the alternative and is not adopted: it needs a virtual environment and a packaging file this project otherwise has no use for, and it puts the four packages on `sys.path` for every interpreter run, so a second checkout would shadow the first in a way nothing in the second checkout records.
- Dependencies: none beyond the standard library. `re`, which Spec_TextFinder.md §6.1 assigns to Python, ships with the interpreter, so this implementation declares no package requirement at all and needs no virtual environment to run.
- The launchers `Python_TextFinder.bat` and `Python_TextFinder` set `PYTHONPATH`, invoke `python -m python_textfinder_entry`, forward their arguments, and return the interpreter's exit code unchanged. `Python_TextFinder` is the name Spec_TextFinder.md §5.1 substitutes for `<executable>` in the help text, and that text is fixed rather than derived from `sys.argv[0]`, which carries the path of `__main__.py` under `python -m` and would otherwise put an interpreter path in the usage line.
- No third-party test framework, per Spec_TextFinder.md §6.2 and the dependency rule of §6. `unittest` is in the standard library, so the suites use it and `pytest` is rejected by name as third-party. Each suite is a script that runs its cases through `unittest` and exits with the number that failed, and the runners invoke those scripts.
- Spec_TextFinder.md §6.2 has a runner build what it is about to run. There is no build here, so each runner does the two things a build would have done for it: it puts the four `src/` folders on `PYTHONPATH`, and it runs `python -m compileall -q` over them, which surfaces a syntax error in any source file before the first suite starts. A `compileall` failure counts every suite the runner would have run as failed and the runner stops there. §6.2's never-built rule still applies: a suite whose script is absent is a failure rather than a pass by absence.
- Annotations are written throughout and are not checked at run time. Running a type checker is not part of running this program, and no checker is required to run it; the annotations are documentation that a checker can also read.

## Notes

- This forms a data pipeline architecture that emits an output immediately following evaluation of a regex match.
- Identifiers follow Python convention, so this implementation spells in snake_case what the C++ implementation spells in camelCase and the C# implementation in PascalCase: `usage_line` for `usageLine` and `UsageLine`, `line_numbers` for `lineNumbers` and `LineNumbers`. The switch letters, the emitted text, and the exit codes are fixed by Spec_TextFinder.md and are identical in all four.
- `ProgramCommands` is a dataclass whose field defaults carry the defaults of Spec_TextFinder.md §5, so a newly constructed instance equals the result of parsing an empty command line.
- The `Output` protocol is the current design choice, and it buys less here than its counterparts do in the siblings. A C++ template instantiation and a Rust monomorphization devirtualize the call; a C# generic over a reference type does not but still bounds the type at compile time. A Python annotation bounds nothing at run time and changes no dispatch — every call is an attribute lookup either way. What the protocol buys is a bound a type checker can hold and a name this document can point at. An `abc.ABC` base class is the alternative and is not adopted: it would make the bound nominal, so a test recorder would have to import `python_textfinder_dirnav` to subclass it, where a protocol lets a test pass any object carrying the one method.
- `StdoutSink` nonetheless names `Output` as a base class, which a protocol permits. That makes the dependency edge above a real import rather than a convention, and lets a checker verify the sink against the protocol at the point the sink is defined. Structural typing still holds for everything that does not subclass it.
- Spec_TextFinder.md §3.4 obliges an implementation to prevent its runtime translating the LF terminator to CRLF. `sys.stdout` is a text stream opened with `newline=None`, which translates `\n` to `\r\n` on Windows, and `print` writes through it, so the interpreter's most obvious way to write a line is the one this specification forbids. `python_textfinder_output` owns a `TextIOWrapper` over `sys.stdout.buffer` with `newline="\n"`, and [Spec_Python_TextFinder_Output.md](Python_Spec_driven_Output/Spec_Python_TextFinder_Output.md) records what follows from that. `print` is not used anywhere in this implementation.
- Python has no destructor that runs deterministically at scope exit. CPython's reference counting usually collects an object at the last reference, and that is an implementation detail rather than a language rule, so the sink implements the context-manager protocol and the binary holds it in a `with` statement. A flush from `__del__` is not relied on for the same reason the C# implementation does not rely on a finalizer.
- `sys.argv` holds the program name in element 0, as C++'s `argv[0]` and Rust's first `args_os()` element do, where C#'s `string[] args` holds the arguments alone. The bare command line of Spec_TextFinder.md §3.1 is therefore a one-element list here, and the parser scans from index 1. Each component spec states its own offset rather than inheriting a sibling's.
- A `str` is a sequence of Unicode scalar values, and the interpreter decodes the command line before `main` sees it — on POSIX with the filesystem encoding and the `surrogateescape` error handler, so an argument that is not valid UTF-8 arrives carrying lone surrogates rather than failing to arrive. The undecodable-argument exit code the Rust implementation defines therefore has no counterpart here. What follows instead is that such an argument can reach the output, and [Spec_Python_TextFinder_Output.md](Python_Spec_driven_Output/Spec_Python_TextFinder_Output.md) §5 fixes what the sink does with it.
- The same `surrogateescape` decoding means a filename that is not valid UTF-8 arrives as text and can be opened, where the C# runtime substitutes U+FFFD and loses the ability to open it. Spec_TextFinder.md §3.4 nonetheless requires such a file be announced rather than searched, so [Spec_Python_TextFinder_Dirnav.md](Python_Spec_driven_Dirnav/Spec_Python_TextFinder_Dirnav.md) §5 runs an explicit name test where the C# implementation needs none. The specification wins over what the language makes easy.
- `Dirnav` holds references to the sink, the skip list, and the parsed commands, and the interpreter keeps them alive as long as it does. The lifetime rule the C++ implementation states in prose and the Rust implementation enforces with a borrow checker therefore has nothing to enforce here, as it has nothing to enforce in C#.
- The skip list is a module-level list in the entry package, reachable without a lock and without an interior-mutability type. The `thread_local!` and `RefCell` pair the Rust implementation needs has no counterpart: the list is built at import time, before traversal begins, and traversal runs on one thread. It is handed to `Dirnav` as a `tuple`, which cannot be modified at all — stronger than the C# implementation's `IReadOnlyList<string>`, which a caller holding the underlying list can still change.
