TextFinder Spec-Driven Design: Introduction

project-level specification - process and product

About Project Repo

1.  Spec-Driven Design

Spec-driven design makes a specification the source used to create code. Every line of the TextFinder implementations derives from a Spec*.md or a *Structure.md document, and a change to the code starts as a change to one of those documents. The specification is not a description written after the fact - it is the input the code is built from. This project contains specifications and code for four implementations using the Rust, C++, C#, and Python programming languages. It also contains markdown documentation of the building and editing of specs and code using AI Claude Code. Almost all of the files were built using AI prompts then edited and refined using additional probing prompts. The project contains four kinds of document. Constitution.md states the rules that bind the whole tree. Spec_TextFinder.md specifies behavior common to every implementation, in no particular language. One *Structure.md per language fixes components and build. One Spec_*.md per component defines the code specific process for creating component files. A fifth kind, Prompts_*.md, records the conversations that produced the others and feeds nothing back into the code.

2.  The Constitution

Constitution.md holds two rules, and both exist to keep the specification the only channel into the code.
  • Spec-driven code. All code creation and modification derives from the Spec*.md and *Structure.md files in the project directory or any subdirectory. Example code, sample implementations, and other projects are excluded as sources. General language knowledge - idioms, standard libraries, toolchains - stays available, because a specification that had to teach C++23 would never end.
  • Stay inside. Nothing outside Spec_driven_TextFinder/ is modified without an explicit request naming the file, and reading outside is confined to standard toolchains, the project CLAUDE.md, auto-memory, and git status and history. The rule bounds the blast radius of a project whose code is generated.
Two notes carry weight beyond the rules. No code lives in the top directory, so every implementation sits in a child. An ambiguous specification is a question to ask, not a gap to fill from an outside source - the alternative is code whose reason for existing appears in no document.

3.  The Project Specification

Spec_TextFinder.md runs seven sections: purpose, scope, functional requirements, command-line syntax, defined switches, non-functional requirements, and non-goals. It specifies the behavior all implementations share and refuses to specify anything language-specific. The C++ implementation came first; Rust, C#, and Python follow, each refining this document without redefining it.

3.1  Functional Requirements

Section 3 divides into five subsections, one per boundary the program has: input, traversal, matching, output, and public interface.
  • Every switch has a default. Per §3.1, a command line with no switches searches the current directory with default settings, so the bare invocation is fully specified rather than left as a special case.
  • Traversal is depth-first in filesystem order. §3.2 descends into a directory at the point the platform's directory-reading facility presents it, files and directories interleaved. TextFinder reorders nothing, so the visit order is the filesystem's own. §6 then records exactly what that leaves guaranteed.
  • The skip list prunes 11 directory names. §3.2 names archive, .git, .svn, .hg, build, out, target, bin, obj, __pycache__, and node_modules, compares each against a directory's basename, and fixes the comparison as case-sensitive on POSIX and case-insensitive on Windows.
  • Three tests admit a file. §3.3 caps size at 10 MB (10,485,760 bytes) from filesystem metadata, then requires the content to hold no NUL byte and to be valid UTF-8. The specification explains why both content tests are needed: a UTF-16 file of ASCII text is valid UTF-8, so UTF-8 validity alone would not detect it.
  • One case reads no file content. When /r is the default . and /n and /L are both false, §3.3 reports every selected file of non-zero size without opening it. The specification states the two consequences it accepts for the speed: a binary file gets reported, and so does a file whose lines are all empty.
  • Output fields join with a three-character separator. §3.4 fixes the record as <path> - <lineNumber> - <matchedLine>, with the second field gated on /n and the third on /L. When both are off a record carries the path alone, so §3.4 emits one record per matching file and stops evaluating that file at its first match.
  • Four announcements report what the walk met. §3.4 defines searched and skipped as file announcements, gated on /h, and too large and cannot open as error announcements, emitted whatever /h says. All four go through the output component, not to stderr, and none affects the exit code.
  • The public interface is one function. §3.5 exposes addSkipDirectory(name), which extends the default skip list rather than replacing it, accumulates across calls, and ignores duplicates. Each language spec fixes the exact name and types.

3.2  Command Line

Sections 4 and 5 specify the command line down to the byte. Every switch is a single case-sensitive letter introduced by / or -, the two introducers being equivalent, so /h and /H denote different commands. Every switch takes exactly one argument as the next whitespace-separated token; §4 states plainly that there are no bare flags. When a switch other than /P repeats, the last occurrence wins. §5 tabulates nine switches with their defaults: /P root path, /p extension list, /r regular expression, /s recursion, /h announcement suppression, /v option listing, /H help, /n line numbers, and /L matched-line text. §5.1 gives the help text as literal text every implementation prints, and §5.2 fixes seven usage diagnostics as reason lines identical across implementations. Fixing that text in the project spec is what lets a test compare two implementations line for line.

3.3  Non-Functional Requirements and Non-Goals

§6 carries three requirements. Portability names Windows and POSIX. Dependencies allow the standard library and, where needed, packages from the language's own ecosystem for regex and filesystem access, and exclude any third-party TextFinder library. Consistency states the reproducibility claim and its limit: implementations produce the same match set in depth-first order, but because §3.2 leaves a directory's entries in filesystem order, the total emission order is reproducible only across runs over the same tree on the same platform and filesystem. §7 lists two non-goals. TextFinder does not modify files, and it does not follow symbolic links or search binary files. Both restate decisions §3 already made, which is the point: a reader looking for a feature finds its absence stated rather than implied.

4.  What Makes the Specification Usable

Five traits recur through Spec_TextFinder.md, and each one removes a decision the implementer would otherwise make alone.
  • Requirements are observable at the boundary. The specification fixes what appears on stdout, what appears on stderr, and what the exit code is. It does not fix data structures, and the C++ structure document is free to choose them.
  • Quantities appear as numbers. 10,485,760 bytes, 11 skip-list names, nine switches, three line terminators, one match per path-only record. Each of those is a test case.
  • Fixed text is quoted, not described. §5.1 and §5.2 reproduce the help text and the reason lines rather than paraphrasing them, so two implementations cannot drift apart in wording.
  • Accepted costs are stated. §3.3's no-content case and §6's ordering limit both name what the design gives up. A specification that hides its trade-offs invites an implementer to fix what was deliberate.
  • Each rule has one home. Switch behavior lives in §4 and §5; traversal, matching, and output live in §3.2 through §3.4. The component specs cite those sections rather than restating them, so the authority for a rule is always one place.

5.  The Process

The documents come in order, each one narrowing what the next may decide.
  1. Write Constitution.md - the rules that bind the tree, and the statement that specifications are the only source of code.
  2. Write Spec_TextFinder.md - behavior common to every implementation, in no particular language.
  3. Write <Lang>_TextFinder_Structure.md - the components, their dependencies, and the build. For C++ that is three libraries and one binary.
  4. Write one Spec_*.md per component - the interface in the target language, each citing the project spec sections it binds.
  5. Build the code from those documents, and from no other source.
  6. Record each conversation in a Prompts_*.md beside the document it produced, and refinements in a Prompts_Fix_*.md.
 Steps 2 through 4 leave a chain of citation rather than a chain of copies. Spec_Cpp_TextFinder_Cmdline.md calls itself the C++ binding of §4 and §5 and names those sections the authority for switch syntax, meanings, and defaults. Spec_Cpp_TextFinder_Dirnav.md does the same for §3.2 through §3.4. Neither restates a rule it could cite, so a correction to the project spec reaches the component specs without being applied twice. Step 6 matters for a project whose code is generated. The Prompts_*.md files hold the reasoning that produced a specification, including the questions asked and the answers given. Project_Tree.md marks them explicitly as records and not inputs to code, which keeps the first rule of the Constitution enforceable: the code derives from the specifications, and the transcripts are there for the reader.

5.1  Excerpt - Spec_TextFinder.md §5.2

This is the section that makes two implementations comparable by test. It fixes the reason lines as literal text, names the exit behavior, and marks the boundary between a diagnostic about what the user typed and a failure that is specified per implementation. 
### 5.2 Usage Diagnostics

A usage diagnostic reports a command line TextFinder will not act on. Every
implementation writes it to stderr as a reason line from the table below, a
newline, then the usage line of §5.1, and exits with a non-zero code.
`<token>` is the offending token and `<switch>` the switch, each reproduced
exactly as typed, preserving the introducer.

| Condition                                                    | Reason line                             |
|--------------------------------------------------------------|-----------------------------------------|
| Token in switch position has no `/` or `-` introducer        | `not a switch: <token>`                 |
| Introducer-led token that is not a switch defined in §5      | `unrecognized switch: <token>`          |
| Switch is the last token, with no argument token following   | `missing argument for switch: <switch>` |
| Boolean switch given a value other than `true` or `false`    | `invalid boolean for <switch>: <token>` |
| /P given an empty argument                                   | `empty root path for switch: <switch>`  |
| /r given an empty argument                                   | `empty expression for switch: <switch>`  |
| /r given an expression the regex engine will not compile     | `invalid regex for switch: /r`          |

These reason lines are fixed text, identical across implementations. Failures
that are not about what the user typed - a search that cannot initialize its
output component, for instance - are not usage diagnostics and are specified
per implementation.
