Spec-Driven Python: Testing

128 unit checks, 34 integration checks, and 31 fixture cases

Process Behavior C++ Rust C# Python
Synopsis:
Four suites and three runners. 128 unit checks across three libraries, 34 integration checks against the assembled program, and 31 fixture cases driven as subtests inside one of them.
  • unittest is in the standard library, so Spec_TextFinder.md §6.2's no-third-party-framework rule admits it and no runner had to be hand-written inside a suite. pytest is rejected by name.
  • §6.2 has a runner build what it is about to run. There is no build here, so each runner puts the four src/ folders on PYTHONPATH and runs python -m compileall -q over them.
The suites are held to properties, not to a transcript, and several exist because a reading of the specification could be wrong in a way nothing else would catch.
  • LF-only stdout asserted at the byte level through a pipe on Windows, before any decoding.
  • The eight terminators str.splitlines() would wrongly split on, one check each.
  • A file at 10,485,760 bytes searched and one at 10,485,761 announced.
  • Every source file parsed with ast.parse(..., feature_version=(3, 10)), which holds the interpreter floor for syntax rather than asserting it.
 Two things were verified by running rather than by reading, and both are worth more than the checks they produced.
  • §6.2's never-built rule: the Output suite was renamed away, the runner reported output - suite not present and exited 1 rather than passing by absence, then the suite was restored.
  • The fixture bites: one expected file was corrupted, the integration suite failed and named the case, then the file was restored.

1.  Four Suites, Three Runners

Spec_TextFinder.md §6.2 asks for a unit suite beside each library and an integration suite driving the assembled program. This implementation has both, plus the shared fixture of Section 4, which the integration suite drives.
Suite Checks What it drives
cmdline unit 53 parse, the three text renderers, and the dataclass defaults, in process
dirnav unit 51 Traversal, admission, splitting, and emission against a temporary tree, through a recording Output
output unit 24 The sink, with sys.stdout and sys.stderr replaced by byte buffers
integration 34 The assembled program as a subprocess, plus the 31 fixture cases as subtests
No third-party test framework, per §6.2 and the dependency rule of §6. unittest is in the standard library, so the suites use it and pytest is rejected by name as third-party. That is the one place this thread had an easier time than the C# thread, which had to write a runner by hand inside each suite because every .NET test adapter arrives as a NuGet package. Each suite is a script rather than a module a framework discovers. Its last four lines are the whole of the contract with the runner: 
if __name__ == "__main__":
    result = unittest.main(exit=False, verbosity=1).result
    sys.exit(len(result.failures) + len(result.errors))
exit=False keeps unittest.main from calling sys.exit with a status of its own, so the script reports the number of failures rather than a boolean. A runner that summed booleans could not tell one broken suite from twenty broken checks. Three runners drive them - run_unit_tests.bat, run_integration_tests.bat, and run_demo.bat - and each does the two things §6.2's build requirement means here.
  • It puts the four src/ folders on PYTHONPATH.
  • It runs python -m compileall -q over them, which surfaces a syntax error in any source file before the first suite starts. A compileall failure counts every suite the runner would have run as failed and the runner stops there.
 There is no build step in this implementation, so compileall is what stands in for one. It is a weaker check than a compiler: it catches a syntax error and not a name error, a wrong argument count, or a type mismatch. That is stated rather than glossed, and it is why the interpreter-floor check of Section 5 parses every source file explicitly rather than trusting that the suites would have imported them all.

2.  The Unit Suites

Each unit suite imports its library through the package name rather than through a file path, so it exercises the same import the binary does. Each sits under the component's test/ folder and is not part of the package, so importing the package does not import the suite. The dirnav suite builds its tree from a dictionary of bytes. Eleven entries, chosen so that each admission and selection rule is reached by at least one of them - three LF lines, a CRLF file, a bare-CR file, an empty file, a file with a BOM, a file holding a NUL, a file of invalid UTF-8, a dot-file, a file with no extension, one level down, and one under a skip-list name. Its Output is a nine-line recorder, which is the case for the protocol being structural rather than nominal: 
class Recorder:
    def __init__(self):
        self.lines = []

    def output(self, text: str) -> None:
        self.lines.append(text)
It inherits from nothing and imports nothing from python_textfinder_dirnav - which is the argument Dirnav Section 2 makes for rejecting abc.ABC, made concrete. Two checks hold both ends of it: the recorder satisfies Output under isinstance, and an object without the method does not. The output suite replaces the interpreter's own streams. It swaps sys.stdout and sys.stderr for objects whose buffer attribute is a BytesIO, so the sink wraps a byte buffer the test can read and every check compares bytes rather than decoded text. A BrokenBuffer subclass whose write raises OSError is what drives the failure paths, and a fixture using it for both streams is what covers the case Section 4 of the Output page describes, where reporting a failure is itself a failure. The cmdline suite needs no fixture at all, the library touching no filesystem and opening no stream. Its one helper prepends a program name to the token list, since parse scans from index 1 and a suite that passed a pre-sliced list would test a different function than the binary calls.

3.  The Integration Suite

The integration suite drives the assembled program as a subprocess - python -m python_textfinder_entry with a working directory of its own - and reads stdout and stderr as bytes as well as as text. Running it as a subprocess is what makes the exit code and the stream bytes observable at all, and it is the only way to check the three exit codes §3.4 fixes. Its 34 checks fall into seven groups.
  • The bare command line - the nine listing lines exactly, an empty stderr, and no run summary, since §3.6 requires none from a run that traversed nothing.
  • Help - the text starts with the usage line, stderr is empty, nothing is traversed, and -H and /H produce identical output, which is §4's introducer equivalence checked rather than assumed.
  • Usage diagnostics - five of the six reason lines, each with an empty stdout and exit 1, and one check that the diagnostic's second line equals the first line of the help text. That last one is the shape §5.2 binds, held against the text §5.1 fixes rather than against a copy of it.
  • The invalid expression - exit 1, the /r line on stdout carrying what failed, exactly nine stdout lines, no traversal, the listing not repeated when /v already wrote it, and stderr exactly two lines. The last is the check that would fail if the interpreter's own re.error text ever reached the user.
  • Search - eight checks over a four-file scratch tree covering the default run, the detail switches, the extension filter, /s false, the verbose listing preceding the output, two roots under one summary, an unopenable root, and a search that matched nothing.
  • Stream bytes - four checks, covered in Section 5.
  • Exit codes and the interpreter floor - the three codes and no other, no traceback on any of six command lines, and the three floor checks of Section 5.
 Every search check names its expected run summary rather than only its paths. /s false over that tree reports accessed 2 files, 1 directories and the default run reports accessed 3 files, 2 directories, so the counts of §3.6 are held by the suite and not only by the demonstration, whose numbers move with the tree.

4.  The Shared Fixture

Spec_driven_TextFinder/Fixture/ is a project-level artifact rather than a Python one, and the Python suite is the first to drive it. It holds one tree of eleven files, cases.txt listing 31 command lines, and expected/ holding one file per case. It exists because comparing four implementations with one another catches a difference and gives no evidence about which side is wrong - and catches nothing at all when two implementations share a misreading, which is the likely failure, since the later implementations are written from documents the earlier ones shaped. A committed artifact turns "the four agree" into "the four agree with something". Each case carries four fields: a name, a comparison mode, an exit code, and the arguments. The mode is the part that makes the artifact portable rather than platform-specific.
  • ordered - stdout must equal the expected bytes exactly. Used where the output has one possible order: a root that is a single file, a listing, the help text, or an empty stdout.
  • unordered - the lines of stdout, sorted, must equal the expected file, which is stored sorted. Used where the output spans a directory whose entry order §3.2 leaves to the platform. The runner additionally checks that the last line emitted, before sorting, is the run summary, since §3.6 fixes that and sorting would otherwise hide it.
 stdout is compared as bytes, not as decoded text, so a CR a runtime inserted is a failure rather than something a line-based comparison would absorb. The fixture does not fix stderr: §2 and §5.2 leave every implementation its own wording there, so a case that exits 1 records what stdout held and what the process returned and says nothing about the text that explained it. .gitattributes in that folder sets * -text. Without it a checkout on Windows would rewrite crlf.txt and cr.md, and three cases would fail for a reason unrelated to the implementation under test. That line is the fixture's one dependency on how the repository stores it, and it is there to remove every other one. The provenance is stated rather than implied, and it is the honest limit of what the fixture is worth. The expected files were captured from the Python implementation on 2026-09-24 and then read against §3 through §5 case by case. They were not derived independently, so a case where this implementation and the specification disagree in the same direction as the reviewer would have been committed as correct. If a case is ever found to contradict Spec_TextFinder.md, the specification wins and the expected file is regenerated - Constitution.md rule 1 applied to a folder of captured output. Three cases exist only because a review found a rule unsettled or unstated. help-outranks-bad-regex and help-outranks-verbose hold §5.4's resolution order, which was unspecified and observable until turn 6. skip-list-never-prunes-a-root holds the §3.2 exemption that is one sentence of prose and easy to lose. The C++, Rust, and C# suites do not drive the fixture yet, which Important_Notes.md N5 records. Until they do, the artifact holds one implementation to the specification rather than four to one another.

5.  What the Suites Hold To

Several checks exist because a reading of the specification could be wrong in a way nothing else would catch. Those are the ones worth naming. LF-only stdout, at the byte level, through a pipe, on Windows. Four command lines are run and each is checked for the absence of \r in the raw bytes and for a terminating \n, before any decoding. A check on decoded text would pass whatever the sink wrote, since a text layer would have absorbed the translation. Two more checks assert that stdout opens with no byte-order mark and that a non-ASCII line reaches the pipe as UTF-8. The eight terminators str.splitlines() would wrongly split on. Vertical tab, form feed, the file, group, record, and unit separators, NEL, and the line and paragraph separators each get a check asserting they do not terminate a line. Those eight are the difference between this implementation's match set and the one the obvious standard call would produce, and no other check in the project would notice it. The size limit from both sides. A file of exactly 10,485,760 bytes is searched; one of 10,485,761 draws too large and is still counted. A limit asserted from one side only is a limit whose comparison operator is untested. The no-content fast path reporting a file it never opened. A binary file is reported by its path line under the default expression, which is §3.3's accepted cost made visible rather than argued for. The same run draws no file announcement under either /h setting. .gitignore selected by /p gitignore. §5 fixes that a dot-file's extension is the text after the dot, and both os.path.splitext and pathlib.Path.suffix disagree. One check holds the rule the standard library would have got wrong. The interpreter floor held for syntax rather than asserted. Three checks: the running interpreter meets 3.10; no source file carries a CR; and every source file parses under ast.parse(text, feature_version=(3, 10)). The third is the one that matters - running on 3.12 and asserting "we support 3.10" proves nothing, while parsing each file at the declared feature version proves it for syntax. It also counts the files it checked and asserts the count is 11, so a source file added and forgotten fails the suite rather than being skipped by it. No traceback on any path. Six command lines - bare, help, a search, an unrecognized switch, a bad expression, and a missing root - are each checked for the absence of Traceback in stderr. That is the claim of Entry Section 6 made falsifiable: an uncaught exception would exit 1 with no usage line, which would read as a usage failure. Three checks for a sink with both streams broken. Nothing escapes when the notice cannot be written, nothing escapes when release is the first failure, and the sink is still released. All three were added in turn 6, after a probe demonstrated the escape rather than after a reading predicted it.

6.  Two Things Verified by Running

A suite that would pass whether or not the thing it tests works is worse than no suite. Two properties of this harness were checked by breaking something on purpose rather than by reading the code that implements them. §6.2's never-built rule. The rule is that a suite that never ran is a failure rather than a pass by absence. The Output suite was renamed away, the unit runner was run, and it reported output - suite not present and exited 1. The suite was then restored. Without that check the runner's if not exist branch is a line of batch nobody has executed. The fixture bites. One expected file was corrupted, the integration suite was run, and it failed and named the case. The file was then restored. A fixture driven through subTest is exactly the shape that can pass vacuously - an empty case list, a mis-joined path, a comparison against itself - so the check is on the comparison rather than on the cases. The case-list length is asserted too, at 31 or more, for the same reason: a cases.txt that failed to parse would otherwise produce zero subtests and a green suite.

7.  Running Them

Two commands, each from the implementation's own folder. Neither needs a virtual environment and neither installs anything. 
run_unit_tests.bat
run_integration_tests.bat

The dirnav suite costs a hundred times what the other two do, and the reason is the only one that touches a filesystem: it writes eleven files to a temporary directory for each of several fixtures. The other two run entirely in memory. The integration runner: 
compiling the four packages

=== integration suite ===
..................................
----------------------------------------------------------------------
Ran 34 tests in 6.520s

OK
integration - exit status 0

0 suite(s) failed
6.5 seconds for 34 checks, against 0.1 for 128. Every check here starts an interpreter, and the fixture check starts 31 of them inside one. That cost is what buys the exit code and the stream bytes, which no in-process check can observe. Each runner holds the console after its summary unless TEXTFINDER_NO_PAUSE is set, which is what lets a capture run unattended and a reader run it by double-clicking.

8.  What the Suites Do Not Cover

Four gaps, each stated in the specification that leaves it.
  • The recursion limit. The traversal is written as recursion, so a tree deeper than the interpreter's limit ends the run with a RecursionError - 1000 frames by default, and the library spends more than one frame per level. No suite exercises it, since no fixture builds a tree of that depth.
  • Symbolic links. §3.2 requires a link be passed over silently, and creating one on Windows needs a privilege a test run cannot assume. The rule is held by the follow_symlinks=False arguments being written out at every call rather than by a check.
  • Unrenderable names. The root-path case is covered - one check passes a root carrying a surrogate and asserts the U+FFFD announcement - and the directory-entry case is not, since creating such a name is a POSIX-only operation.
  • The skip-list extension point. §3.5 makes it a build-time facility with no runtime path, and no suite calls _add_skip_directory, which is the rule that gives the leading underscore its meaning. The defaults it starts from are covered by the pruning checks.
 The first three are properties of the platform rather than of the harness, and naming them here is what keeps a reader from mistaking a green suite for full coverage of §3.2.
