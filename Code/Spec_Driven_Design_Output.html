TextFinder Spec-Driven Design: Output

the sink, and what it refuses to know

About Project Repo

1.  Purpose

Cpp_TextFinder_Output is the sink. It receives fully formed strings from Cpp_TextFinder_Dirnav, writes each as one line to stdout, and absorbs every write failure so that neither the traversal nor the binary has to reason about it. The whole library is 44 lines, and most of what there is to say about it concerns what it does not do.

2.  Public Interface

export module Cpp_TextFinder_Output;

import std;
import Cpp_TextFinder_Dirnav;

export class Cpp_TextFinder_Output : public Output {
public:
    Cpp_TextFinder_Output();
    ~Cpp_TextFinder_Output() override;
    void output(const std::string& text) override;
};
The class takes no configuration, and Spec_Cpp_TextFinder_Output.md §4 gives the reason: Cpp_TextFinder_Dirnav formats every record and announcement in full before emitting it, so nothing is left here to parameterize. The library cannot tell a record from an announcement, and does not apply /h, /n, or /L; all of that is settled before a string arrives. output writes the string unchanged, followed by one LF, and adds nothing else - no prefix, no separator, no trailing content. The constructor is the only member that can fail. Once constructed, the object never throws and never reports failure to a caller.

3.  Line Termination

Spec_TextFinder.md §3.4 terminates every record and announcement with a single LF on every platform, and requires an implementation to prevent its runtime from translating that terminator. Without the rule, the same tree would yield byte-different output on Windows and POSIX, and the line-for-line comparison §6 permits would hold only within a platform. The constructor meets that with _setmode(1, _O_BINARY) on Windows, file descriptor 1 being stdout, and throws std::runtime_error when the call fails. Cpp_TextFinder_Entry catches it and exits 1 with cannot initialize output. The <io.h> and <fcntl.h> includes sit in the global module fragment, since a module interface unit admits preprocessor includes only there. On POSIX the block compiles away and no mode change is needed. The Output unit suite redirects std::cout and inspects the bytes, asserting that no CR reaches the stream and that an empty string still terminates a line.

4.  Failure Absorption

A write that fails, through a closed pipe or a full disk, sets failed_. The first such failure puts the single line output failed on stderr; every string after that is discarded silently, with nothing written to stdout or stderr again. Spec_Cpp_TextFinder_Output.md §6 fixes the three things that do not happen. The library never throws after construction, never returns a status, and never lets the failure reach Cpp_TextFinder_Dirnav, which goes on traversing. A failed write does not change the exit code, which Spec_Cpp_TextFinder_Entry.md §6 reserves for command-line and startup failures. The result is that a caller writing to a pipe that closes early finishes its walk rather than aborting partway through.

5.  Buffering

No flush happens per record. Flushing each line would dominate the runtime of a search that emits many, and Spec_TextFinder.md §3.4 requires only that matches be written as they occur, not that they reach the device immediately. The stream flushes in the destructor, which Cpp_TextFinder_Entry reaches before returning from main. Spec_Cpp_TextFinder_Output.md §7 states why deferring is safe here: every stderr write in this implementation is one of the three startup diagnostics of Spec_Cpp_TextFinder_Entry.md §4, each preceding traversal and followed at once by process exit, so no buffered stdout content can appear after a stderr line that logically precedes it. The constructor also calls std::ios::sync_with_stdio(false), which detaches the C++ streams from C stdio.

6.  Source - Cpp_Spec_driven_Output/src/Cpp_TextFinder_Output.ixx

// Cpp_TextFinder_Output.ixx - the stdout sink, per Spec_Cpp_TextFinder_Output.md

module;

#ifdef _WIN32
#include <io.h>
#include <fcntl.h>
#endif

export module Cpp_TextFinder_Output;

import std;
import Cpp_TextFinder_Dirnav;

export class Cpp_TextFinder_Output : public Output {
public:
    Cpp_TextFinder_Output();
    ~Cpp_TextFinder_Output() override;
    void output(const std::string& text) override;

private:
    bool failed_{false};
};

Cpp_TextFinder_Output::Cpp_TextFinder_Output() {
    std::ios::sync_with_stdio(false);
#ifdef _WIN32
    // File descriptor 1 is stdout. Binary mode keeps the LF that Spec_TextFinder.md §3.4
    // fixes as the terminator from being translated to CRLF.
    if (_setmode(1, _O_BINARY) == -1) throw std::runtime_error{"stdout cannot be set to binary mode"};
#endif
}

Cpp_TextFinder_Output::~Cpp_TextFinder_Output() { std::cout.flush(); }

void Cpp_TextFinder_Output::output(const std::string& text) {
    if (failed_) return;

    std::cout << text << '\n';
    if (!std::cout) {
        failed_ = true;
        std::cerr << "output failed\n";
    }
}

### Assistant

Created [Spec_Cpp_TextFinder_Output.md](Spec_Cpp_TextFinder_Output.md) with nine sections, in the shape of the other two library specs:

1. **Purpose** — the sink; receives fully formed strings, writes each as one line, absorbs write failures.
2. **Scope** — what is emitted and under what gating belongs to Spec_TextFinder.md §3.4 and `Cpp_TextFinder_Dirnav`.
3. **Responsibilities** — derives from `Output`, prepares stdout, writes lines, absorbs failures.
4. **Public Interface** — `Cpp_TextFinder_Output : public Output` with a default constructor, destructor, and the one override.
5. **Destination and Line Termination** — stdout, one LF per call, on every platform.
6. **Error Handling** — constructor throws; after construction nothing throws or returns a status.
7. **Buffering and Flushing** — no per-record flush; flush at destruction.
8. **Build** — CMake library target, C++ module, depends on `Cpp_TextFinder_Dirnav` for the `Output` base class.
9. **Non-Goals** — no formatting, no `/h`, `/n`, or `/L` gating, no file or command-line reading, no usage diagnostics.

Reported one contradiction between existing documents. Entry §3 and §4 step 4 said `Cpp_TextFinder_Output` is constructed with "formatting information derived from the parsed commands" — a decision from the Cmdline review — but `Cpp_TextFinder_Dirnav` had since been given all the formatting, leaving nothing for this library to parameterize. Specified a constructor taking no configuration, said so plainly in §4, and left Entry untouched pending authorization.

That left `cannot initialize output` with no cause, so the constructor was given real work: putting stdout into binary mode on Windows, where the C runtime would otherwise translate each LF into CRLF and make the same tree produce byte-different output on Windows and POSIX, quietly limiting the line-for-line comparison of Spec_TextFinder.md §6 to a single platform. A failure to set that mode throws, which is the failure Entry already handles, mirroring how `Cpp_TextFinder_Dirnav` signals a bad regex.

Flagged two smaller decisions and one naming defect:

- A failed write emits one `output failed` line to stderr before the library goes silent, reading Cpp_TextFinder_Structure.md's "handles output errors internally" as not propagating to callers rather than as saying nothing.
- Flushing is deferred to destruction rather than performed per record; §7 shows this is safe here, because every stderr write in Entry precedes traversal and is followed at once by process exit.
- The `Output` abstract base class named its parameter `match_str` in Cpp_TextFinder_Structure.md and Dirnav §4, though announcements flow through it too.
