Spec-Driven Design: Context

what an LLM forgets between requests, and how much of the Spec driven process that explains

Process Behavior C++ Rust C# Python References
Synopsis:
This page explains the one fact about language models that shapes the rest of the Spec driven page set, and it ends by saying how much of the process that fact actually accounts for.
  • A model keeps nothing between requests, so the whole conversation travels on every call.
  • Context accumulates, costs more as it grows, and is eventually discarded.
  • The documents in the project tree exist outside the context and outlive it.
  • About half the process follows from that. The other half is ordinary design.

1.  The Model Holds Nothing Between Requests

A language model does not remember the previous turn, the file it just read, or the correction it just accepted. Every request sends the entire conversation again - the system prompt, each earlier user turn, each earlier model response, and the full text of every file the tools opened along the way. The model is stateless; the transcript carries the state, and the transcript travels on every call. A provider does not run one copy of a model. It runs a fleet - the set of all servers currently loaded with the same model weights, each one holding an identical copy in accelerator memory and each one able to answer any request addressed to that model. A request arrives at a front end that picks a member of the fleet and forwards the work there; the next request in the same conversation may well go somewhere else. Fleet size tracks demand, so machines join and leave while conversations are in flight. Statelessness is a serving decision, not a limitation of the model. A request lands on whichever member of the fleet has capacity, because no member holds anything the request needs. Machines drain, restart, or fail without losing a conversation, and the provider runs its accelerators near saturation instead of reserving memory for sessions idling while a reader thinks about the last answer. Pinning a conversation to one machine would bind that machine's memory to someone who may never send another turn. Providers do keep computed prefixes around, opportunistically and briefly, which is what prompt caching means. That is a cache rather than session state. A hit saves the work of reprocessing a prefix the model has seen before; a miss costs recomputation, not correctness, because the request already carries everything the model needs. Nothing in a conversation depends on the cache being there.

2.  What Travels on Every Request

A conversation that feels incremental to the reader is not incremental on the wire. Turn twenty resends turns one through nineteen. What arrives at the model looks like this:
Part of the request How it behaves as the conversation runs
System prompt and tool definitions Fixed size, resent every time
Project instructions the tool loads automatically Fixed size, resent every time
Prior user turns and model responses One more pair per exchange, never removed
Tool results - file reads, test output, directory listings The dominant growth in a coding session, and the least visible
The current request The only part the reader actually typed
The fourth row is the one that surprises people. Typed dialogue is small. A single read of a specification puts the whole file in the window and leaves it there, and a run of the test suite does the same with its output. A session that looks like a short conversation can be carrying most of a project tree.

3.  Three Consequences

  1. Cost and latency track conversation length, not request size. A one-line request late in a session costs more to answer than the same line early in one. Prompt caching blunts this but does not remove it.
  2. The window is finite, so a long session compacts. Earlier turns get summarized and the originals are gone. A summary preserves the gist of a decision, not its wording, and specifications live or die on wording.
  3. Everything still in the window competes for attention. A stale requirement from turn three argues with the corrected one from turn thirty. Both are present, both look like instructions, and nothing marks the first as superseded.
 The third consequence is the one that costs correctness rather than money. The first two announce themselves - a slow response, a compaction notice. A model acting on a requirement the reader retracted twenty turns ago produces working code that satisfies the wrong specification, and nothing in the session reports it.

4.  What the Document Set Does About It

Context accumulates and then it is discarded - by compaction, by /clear, by closing the session, by starting work on another machine. A requirement that exists only in the conversation survives none of those. The Spec*.md and *Structure.md files live in the project tree, outside the context, and get read back into a fresh one on demand. Constitution.md's rule that all code derives from those files is, read this way, a rule about durability: it puts every binding decision somewhere the next conversation can find it. Partitioning one specification into a language-agnostic parent plus per-language children follows the same reasoning. Generating the Rust implementation loads the constitution, the parent specification, and the Rust documents, and carries none of the C++, C#, or Python detail into the window. The parts of the project that cannot affect the work do not compete for attention with the parts that can. Prompts_*.md files are records rather than inputs for a related reason. A conversation is evidence of how a document reached its content, not an authority competing with it. Replaying a prompt record into a new session would reintroduce exactly the superseded turns that compaction removes, which is the third consequence above, deliberately reproduced.

5.  What Context Explains, and What It Does Not

It would be easy to read the preceding sections as saying that spec-driven design is a workaround for a model limitation. It is worth being precise about how much of the process actually follows from the finite window, because a practice that survives an unlimited one is a practice worth keeping.
Practice What context contributes With an unlimited window
All code derives from the specification documents The transcript is lost; the tree is not Holds. Review, source control, and the next reader all need a document
Parent specification plus per-language children Loads only the documents one language needs Holds in part. The split is also interface against implementation, which is ordinary design
Component specifications under each structure document Keeps a generation request to the components it touches Holds in part. A component is also the unit a reviewer reads
An ambiguity is a question, not a gap to fill A guess made in conversation leaves no trace in the tree Holds. A guess is wrong as often with a large window as with a small one
Prompts_*.md are records, never inputs Replaying them reintroduces corrected requirements Holds. Evidence of a decision is not authority over it
So the window explains why these practices are enforced rather than merely recommended, and it explains the partitioning in detail. It does not explain the practices themselves. Every row above is something a careful team would want from a project worked on by four people over two years, with or without a model involved. Statelessness forces the question where does this decision live on the first day instead of the first handover, and it makes the cost of answering badly immediate rather than deferred. The threads take it from here. The Process introduction lays out the goals, the six threads, and the documents in the order their authority runs; the Constitution states the two rules the whole tree obeys.
