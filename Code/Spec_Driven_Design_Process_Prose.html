1.  Two Documents That Govern Output

The project generates its own documentation. These pages were written from the same tree the code was, so the rules for that output are themselves project artifacts with their own prompt records, sitting beside Spec_TextFinder.md rather than above it. Two documents divide the work. Text_Tone.md fixes the voice: what a sentence looks like, what words are banned, how an identifier is spelled in prose. Page_Structure.md fixes the set: which pages exist, what each covers, and how a reader moves among them. Neither binds code, so neither is a Spec*.md under Constitution rule 1. They bind pages. Code/PageExample.html is the reference implementation for the page shell and the navigation mechanism, and both documents defer to it: Text_Tone.md takes its voice from that page's three prose regions, and Page_Structure.md takes the three navigation mechanisms it supplies.

2.  Text_Tone.md

Four rules override the reference page, and the document states each as a correction rather than a preference.
  • Prefer active voice. Name the actor. The document quotes one of the reference page's own sentences and converts it: "all seven options are printed" becomes "the verbose block prints all seven options."
  • Drop hyperbole. No "powerful", "seamless", "elegant", "dramatically", "vastly". The reference page calls one idiom "nice", which the rule marks as the ceiling rather than the target.
  • Minimize adjectives. Cut any adjective that survives deletion without loss.
  • No em dashes outside Markdown. In HTML pages, source files, code comments, and scripts, an aside takes a spaced hyphen.
 Three further sections do the day-to-day work. Sentence shape asks for declarative present tense, one idea per sentence, and a concrete subject: CmdLine parses argv rather than argv parsing being performed. Naming code in prose requires identifiers, filenames, switches, and literal output inside <code> or backticks, spelled exactly as the source spells them, and requires a claim taken from a specification to cite its section - because a reader who disagrees needs to know where to argue. Structure requires numbered sections, each with an anchor, and puts the source last: prose explains what to look for, then the reader looks. The document ends with a before-and-after table of five rewrites and a seven-item checklist. It is written under its own rules, so it demonstrates them. The em-dash rule shows how a rule gets scoped by contact with the tree. As first written it covered everything, and the reply that created the file reported what that implied: the project documents held 254 em dashes across 24 files. The user narrowed the rule to non-Markdown files in the next turn, which settled all 254 at once, since every one of them sits in a .md file. The other side of the boundary held exactly one violation, a comment in main.cpp, which was replaced with a spaced hyphen.

3.  Page_Structure.md

Page_Structure.md fixes 42 pages across six threads and is written over four placeholders rather than over any language name. [lang] is the file-name token, [part] a page position, [index] a page's place in its own thread, and [ext] the source extensions one implementation's demonstration searches. Their values are fixed in its §0 and nowhere else. Three decisions in it carry most of the structure.
  1. Every language thread links the same eight pages. That is what makes the header row a cross-thread mechanism: from the Cmdline page of one language, another language's entry points at its own Cmdline page. Crossing goes by part name rather than by index, so a language that divides differently links its non-matching parts to its thread's first page.
  2. One page-list file per thread, and one cookie key shared by all of them. Each page loads its own thread's buildPages() and then writes its own 0-based index to the #pages cookie. The shared key is what makes thread switching work: the page a reader arrives on rewrites the index to its own position in its own list, and stepping from there walks the new thread.
  3. A page exists once it is written, not once its code runs. A language thread is created whole, eight pages at once, and a page needing a result only a running implementation can supply states that the result is pending. Pending content is a condition of a page, never a missing page, so the eight indices never change meaning as an implementation fills in.
 §8 assigns the prompt records, and it decides by directory level before it decides by subject. A record produced at the project level goes to the Process thread; one produced inside a language's directory goes to that language's thread. Within the thread, the document a record produced picks the page. The level rule deciding first is what keeps a record off the Behavior thread even where a Behavior page discusses the same document: Spec_TextFinder.md is discussed by one Process page and all five Behavior pages, and its records sit on the Process page. Under that rule no page carries more than two records, against the five and six the earlier structure gave two pages. One row was added later, and the occasion is worth recording because it is what §8 says should happen. A record of reviewing a finished implementation - its idiom, its smells, and the defects the review fixes - matched no row, and the catch-all written for demonstration records would have sent it to a Demonstration page it did not belong on. §8 settles that case against itself: its tables are the authority, and a reading of the rule that disagrees with them obliges the rule to change. So the table gained a row routing such a record to that language's Process page, no component page owning a review that ranges over every component at once. A language now contributes 15 records at most rather than 14, and the two-per-page ceiling above excepts a Process page, which carries three once its language has been reviewed. The document reached its placeholder form by being told it had not. An intermediate draft named C++ files throughout, and the user's correction is worth quoting for what it fixes: "There is no reason for a language specific name to be used in the Structure file as long as it is clear where a language specific name goes in a generated page." The draft had been an instance of the structure rather than the structure. The definitions collected into §0, a language name then appeared in exactly three lines, all inside that table, and §9 stopped being a migration plan for six existing files and became four checks that apply to any page in any thread.

4.  Why the Rules Are Project Artifacts

Both documents started outside the project and were moved in. Text_Tone.md was created at the site root, beside CLAUDE.md, on the reasoning that it governs prose across the whole site; the user moved it to the project root two turns later. The move broke its link to PageExample.html, a repair was offered and rejected, and the stale link then failed for real and was fixed in the following turn. That sequence is in the record because it is the kind of thing a reader of a generated page needs to distinguish from a defect in the generator. Keeping the rules inside the project has two consequences worth stating. Constitution rule 2 binds them, so they move and change only on request like every other file in the tree. And they are inputs to the pages the way a specification is an input to code: a page that disagrees with Page_Structure.md is corrected by rewriting the page, and a structure that is wrong is corrected by amending the document first. One asymmetry remains and is deliberate. These documents are not Spec*.md files, so Constitution rule 1 does not make them authoritative for code, and nothing in them can change the program. They govern what these pages say about it.
