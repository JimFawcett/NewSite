Spec-Driven Python: Structure

four packages, one dependency chain, and no build step

Process Behavior C++ Rust C# Python

1.  Four Packages, One Folder

The Python_TextFinder project comprises three libraries and one binary, arranged as four importable packages under one folder. The shape is the one all four implementations share, and Python_TextFinder_Structure.md takes it from Spec_TextFinder.md rather than from a sibling.
Package What it does
python_textfinder_cmdline Parses the command line into a ProgramCommands object. The single place switch letters, argument syntax, and defaults are known.
python_textfinder_dirnav Directory navigation. Reads file contents, runs regex matching, formats each matching file into the block §3.4 fixes. Defines the Output protocol.
python_textfinder_output The sink. Implements Output.output and handles output errors internally.
python_textfinder_entry The binary. Imports the three libraries, owns the skip list, drives traversal, and returns the exit code.
Each library's package name matches its component name lower-cased with underscores, as Python names a package. The types inside carry their own names rather than the package's: the sink is StdoutSink in python_textfinder_output, so that from python_textfinder_output import StdoutSink reads as a type being imported from a place rather than a name being imported from itself. Each component has its own folder holding its Spec_*.md, its package under src/, and - for the three libraries - its unit suite under test/, which Spec_TextFinder.md §6.2 asks to live beside the code it tests. The integration suite and the demonstration drive the assembled program, so both sit at the root of the folder rather than in a component folder, as do the three runners and the two launchers.

2.  The Dependency Chain, and What Holds It

The binary imports all three libraries. The libraries themselves form a chain: 
python_textfinder_entry
    imports python_textfinder_cmdline, python_textfinder_dirnav, python_textfinder_output

python_textfinder_output
    imports python_textfinder_dirnav          (for the Output protocol)

python_textfinder_dirnav
    imports python_textfinder_cmdline         (for ProgramCommands)

python_textfinder_cmdline
    imports nothing in this project
Nothing imports python_textfinder_output but the binary. The sink is passed to Dirnav at the point of construction, so the traversal knows the protocol and not the type that satisfies it. Each library is a separate package rather than a module of one package, so the chain above is visible as an import graph rather than as a convention inside one namespace. That is the whole of what the arrangement buys, and the document is explicit about what it does not buy. Python enforces no such chain. Any package on sys.path may import any other, and the chain is a rule these specifications state rather than one a tool holds. That is a stated difference from the C++, Rust, and C# implementations, where the build refuses a dependency the structure does not declare - a C++ module that imports an undeclared module does not compile, a Rust crate that names an undeclared dependency does not resolve, and a C# project that references an undeclared assembly does not build. The document says so rather than claiming a guarantee. A reader comparing the four implementations should know that this one's architecture is documented and the other three's is also checked. StdoutSink names Output as a base class, which a typing.Protocol permits. That makes the dependency edge above a real import rather than a convention, and lets a checker verify the sink against the protocol at the point the sink is defined. Structural typing still holds for everything that does not subclass it, which is what lets a test recorder satisfy the protocol without importing the traversal package at all.

3.  No Build Step

Language: Python. Interpreter minimum: CPython 3.10. Build system: none - Python compiles on import, so this implementation has no build step and no build definition. Dependencies: none beyond the standard library. re, which §6.1 assigns to Python, ships with the interpreter, so this implementation declares no package requirement at all and needs no virtual environment to run. The floor is 3.10 and two features fix it. str.removeprefix, which Cmdline needs for the one-dot strip of §5, arrived in 3.9. PEP 604 made X | Y a type expression evaluated at run time, which is what ProgramCommands | ParseFailure is, and that arrived in 3.10. The integration suite holds the claim for syntax rather than asserting it: one check parses every source file with ast.parse(..., feature_version=(3, 10)). Imports resolve through PYTHONPATH, which carries the four src/ folders. The launchers and the runners set it; a reader invoking the interpreter directly sets it too. An editable install through pip is the alternative and is not adopted. It needs a virtual environment and a packaging file this project otherwise has no use for, and it puts the four packages on sys.path for every interpreter run, so a second checkout would shadow the first in a way nothing in the second checkout records. §6.2 has a runner build what it is about to run, and there is no build here. Each runner therefore does the two things a build would have done for it: it puts the four src/ folders on PYTHONPATH, and it runs python -m compileall -q over them, which surfaces a syntax error in any source file before the first suite starts. A compileall failure counts every suite the runner would have run as failed and the runner stops there. §6.2's never-built rule still applies: a suite whose script is absent is a failure rather than a pass by absence. The Testing page covers how that was verified by test rather than by reading. Annotations are written throughout and are not checked at run time. Running a type checker is not part of running this program, and no checker is required to run it; the annotations are documentation a checker can also read.

4.  Naming, and What It Does Not Change

Identifiers follow Python convention, so this implementation spells in snake_case what the C++ implementation spells in camelCase and the C# implementation in PascalCase: usage_line for usageLine and UsageLine, line_numbers for lineNumbers and LineNumbers. The switch letters, the emitted text, and the exit codes are fixed by Spec_TextFinder.md and are identical in all four. A reader who mistook the naming difference for a behavioral one would be reading the wrong document: nothing a language convention touches reaches stdout. Three decisions the structure document records that follow from the language rather than from the design:
  • ProgramCommands is a dataclass whose field defaults carry the defaults of §5, so a newly constructed instance equals the result of parsing an empty command line.
  • sys.argv holds the program name in element 0, as C++'s argv[0] and Rust's first args_os() element do, where C#'s string[] args holds the arguments alone. The bare command line of §3.1 is therefore a one-element list here, and the parser scans from index 1.
  • A str is a sequence of Unicode scalar values, and the interpreter decodes the command line before main sees it, so the undecodable-argument exit code the Rust implementation defines has no counterpart here.
 Each component spec states its own offset rather than inheriting a sibling's, which is the rule that kept the second item above from being assumed in three places and stated in none.

5.  Where the Language Forced a Different Answer

The structure document records six places where Python does not merely rename what a sibling does. Each is settled in the component that owns it, and each is linked from here.
  • Free functions. Cmdline's four entry points are module-level functions, not static methods of a class. The C# structure exists to work around the absence of free functions, so it does not carry over. See Cmdline Section 2.
  • The seam buys less here. A C++ template instantiation and a Rust monomorphization devirtualize the call; a C# generic still bounds the type at compile time; a Python annotation bounds nothing at run time and changes no dispatch. See Dirnav Section 2.
  • print and sys.stdout are forbidden implementation-wide. sys.stdout is opened with newline=None and translates \n to \r\n on Windows, so the interpreter's most obvious way to write a line is the one §3.4 forbids. See Output Section 2.
  • No deterministic destructor. CPython's reference counting usually collects at the last reference, and that is an implementation detail rather than a language rule, so the sink implements the context-manager protocol and the binary holds it in a with statement. A flush from __del__ is not relied on, for the same reason the C# implementation does not rely on a finalizer.
  • Unrenderable names resolve the opposite way from C#. The surrogateescape handler means such a file can be opened here, and §3.4 requires it not be searched, so this library runs an explicit test where C# needs none. See Dirnav Section 4.
  • No lock and no interior-mutability type. The skip list is a module-level list built at import time, traversal runs on one thread, and it is handed over as a tuple. The thread_local! and RefCell pair the Rust implementation needs has no counterpart. See Entry Section 5.
 One item on that list runs against this implementation and is stated in the same voice as the rest: _SKIP_LIST and _add_skip_directory carry a leading underscore, which is the whole of Python's access control where C# has private and C++ has internal linkage. Dirnav holds references to the sink, the skip list, and the parsed commands, and the interpreter keeps them alive as long as it does. The lifetime rule the C++ implementation states in prose and the Rust implementation enforces with a borrow checker therefore has nothing to enforce here, as it has nothing to enforce in C#.

6.  Suites, Runners, and Launchers

No third-party test framework, per §6.2 and the dependency rule of §6. unittest is in the standard library, so the suites use it and pytest is rejected by name as third-party. That is the one place this thread had an easier time than the C# thread, which had to hand-write a runner inside each suite because every .NET test adapter arrives as a NuGet package. Each suite here is a script that runs its cases through unittest and exits with the number that failed, and the runners invoke those scripts.
  • run_unit_tests.bat - compiles the four packages, then runs one unit suite per library.
  • run_integration_tests.bat - compiles, then drives the assembled program end to end.
  • run_demo.bat - compiles, supplies the capture date, then runs the demonstration.
 The launchers Python_TextFinder.bat and Python_TextFinder set PYTHONPATH, invoke python -m python_textfinder_entry, forward their arguments, and return the interpreter's exit code unchanged. Python_TextFinder is the name §5.1 substitutes for <executable> in the help text, and that text is fixed rather than derived from sys.argv[0], which carries the path of __main__.py under python -m and would otherwise put an interpreter path in the usage line.

Eleven source files across four packages, 552 lines of them. Three unit suites and one integration suite add 1,175 lines, so the suites outweigh the implementation by better than two to one - a ratio the Testing page reads against what the suites hold to. Each __init__.py re-exports its package's public names and declares __all__, so the import lines in every other file name a package rather than a module inside it. The unit suites sit under test/ and are not part of any package, so importing a package does not import its suite.
