1.  Five Document Kinds

The project carries five kinds of document. Two of the five bind code, one records how the others were written, and one is a map.
Kind Binds code Scope
Constitution.md indirectly The whole tree. Names which files bind code and where work may reach
Spec_TextFinder.md yes Every implementation. Language-neutral behavior
[lang]_TextFinder_Structure.md yes One language. Components, dependency direction, build, and the one interface declaration
Spec_[lang]_TextFinder_*.md yes One component of one language. The interface in that language
Prompts_*.md no Records of the conversations that produced the rest
Project_Tree.md sits outside that classification. It lists every file with a legend line and binds nothing; Section 5 reproduces it. The Prompts_*.md exclusion is stated in Constitution.md rather than left to convention, and it was tightened once: the second turn of the constitution's refinement asked that these files be marked as documenting the design process and not usable as input for creating or editing code. Without that line a design conversation becomes an unwritten requirement, and the specification stops being the whole of what the code derives from.

2.  The Order They Come In

Each document narrows what the next may decide, and the project was built in that order.
  1. Constitution.md first, so the rules were in place before any specification existed.
  2. Spec_TextFinder.md next, fixing behavior for all four languages while no language had been chosen.
  3. Cpp_TextFinder_Structure.md, naming three libraries, one binary, the dependency direction, and the build.
  4. Four component specifications - Entry, Cmdline, Dirnav, Output - each written against the two documents above it.
  5. Code, from those documents alone.
  6. Tests and a demonstration, against the same documents.
 The order is visible in the records. The Cmdline specification was written with the instruction to use the project specification as an example of content and the Entry specification as an example of structure and style; the Dirnav specification was written the same way against Cmdline; and the Output specification against the project spec and Dirnav. Each new document had two documents above it and one beside it. Order does not mean a document stops changing once the next one starts. It means a later document cannot redefine an earlier one. §2 of the project specification says each implementation "refines this document without redefining it", and the ten rules promoted out of the C++ Dirnav specification moved up rather than down for exactly that reason.

3.  The Citation Chain

A component specification does not restate the rule it implements. It cites the section that fixes it. The chain runs from a line of code to the project specification in three or four hops.
Hop Example
Code cites its component spec // §7: the three admission tests of Spec_TextFinder.md §3.3. in Cpp_TextFinder_Dirnav.ixx
Component spec cites the project spec Dirnav §7 opens "A selected file is put to the three admission tests of Spec_TextFinder.md §3.3"
Component spec cites the structure doc Each Build section reads "Per Cpp_TextFinder_Structure.md", which holds the language level and toolchain floors once
Component spec cites its siblings Output §4 cites Spec_Cpp_TextFinder_Entry.md §4 step 2 for who constructs it
The chain is bidirectional in practice. A component specification names its consumer in the opening paragraph - the Cmdline spec names Entry, the Dirnav spec names Entry and Cmdline, the Output spec names Dirnav and Entry - so a reader who arrives at any one document can reach both the rule above it and the component that depends on it.

4.  Why a Spec Cites Rather Than Restates

A correction applied to a citation reaches every component at once. A correction applied to four copies reaches them one at a time, and reaches three of them wrong. The records measure the cost of the alternative. A review of the Cmdline specification found the switch table in four places - the project spec's §5, the ProgramCommands field comments, the Cmdline spec's own table, and the verbatim help block - and the /P accumulation rule stated five times. The fix removed the Cmdline table and left the struct's field comments carrying the mapping and its initializers carrying the defaults, which is why the C++ spec now says the initializers are "the sole authority in code for the defaults of Spec_TextFinder.md §5." A later pass found the same duplication in the Build sections: the toolchain minimums appeared verbatim in three component specifications and Language: C++23 in those three plus the structure document, making any floor change a four-place edit. All of it moved to the structure document, leaving each component's Build section with its own target name and its module-versus-translation-unit status. Two redundancies survived every pass, and both survived deliberately. §5.1's help text and §5.2's diagnostic table repeat what §5 already says, because that repetition is the fixed text a test compares against. And two warnings in the C++ Dirnav spec were kept by name - std::filesystem::path::extension() disagrees with §5 on dot-files, and directory_iterator yields entries in an unspecified order - on the ground that each stops an implementer writing something plausible and wrong.

## Legend

- `Constitution.md` — governing rules for this project (`Spec_driven_TextFinder/` and its children)
- `Spec_*.md` — behavioral specifications; authoritative source for code
- `*Structure.md` — project/component structure; authoritative source for code
- `Prompts_*.md` — records of the spec-driven design conversations; not inputs to code
- `Prompts_Fix_*.md` — records of subsequent refinement conversations for the same artifact
- `Prompts_Fix_Spec_Cpp_TextFinder.md` — refinements reaching across every C++ component and the project spec
- `Prompts_Build_Cpp_TextFinder.md` — record of turning the C++ specifications into working code
- `Prompts_Cpp_Spec_driven_TextFinder_Tests.md` — record of building and running the test suites
- `Prompts_Final_Tweaks_TextFinder.md` — record of the switch-default, first-match, and demonstration changes
- `src/` — implementation of the sibling `Spec_*.md`, one per component
- `*_UnitTest.ixx` — tests for that component, exporting one entry point; `*_TestDriver.cpp` runs it
- `Cpp_TextFinder_IntegrationTest.ixx` — drives the built executable end to end, covering the Entry binary
- `Cpp_TextFinder_Demo.ixx` — runs the executable against this project's own tree and shows the output
- `run_unit_tests.bat`, `run_integration_tests.bat` — run the suites, announcing each and its exit status
- `run_demo.bat` — runs the demonstration
- `CMakeLists.txt` — build definition; the top-level one configures the whole project
