Spec-Driven Python: Entry

87 lines that wire three libraries together and own the exit codes

Process Behavior C++ Rust C# Python
Synopsis:
This page covers python_textfinder_entry, the binary. It parses the arguments, wires the three libraries together, drives traversal, and owns the skip list and the exit codes.
  • main(argv) is a function a suite can call with an argument list of its own. __main__.py holds three lines and nothing else.
  • Every exit is a return. sys.exit appears once in the component, after the with statement has already ended, and os._exit appears nowhere.
The sink is constructed inside a try and then held by a with, and splitting the two is the point.
  • with StdoutSink() as sink: would put the construction inside the statement, where an except covering the body would also cover the body's own failures.
  • This is the Python counterpart of the C++ implementation's std::optional and of the C# split between a try and a using.
  • Only a return leaves the with statement and releases the sink, which is what flushes the buffer.
 Two things this implementation has that no sibling does, and one it has to give up.
  • sys.argv is already decoded, so the undecodable-argument exit code the Rust implementation defines has no counterpart here.
  • The skip list is handed over as a tuple, which cannot be modified at all - stronger than C#'s IReadOnlyList.
  • Against that, _SKIP_LIST and _add_skip_directory carry a leading underscore, which is the whole of Python's access control. The specification calls that a stated weakness rather than a difference in design.

1.  The Binary

python_textfinder_entry is the command-line entry point. It parses the program's arguments, wires the three libraries together, and drives directory traversal. Matching and file I/O belong to python_textfinder_dirnav and python_textfinder_output; the binary performs neither. The binary does write process-level text of its own - help, the resolved option listing, and startup diagnostics - but it composes none of it. Each is a string python_textfinder_cmdline hands it, and the binary decides only when to write it and to which stream. Block lines and announcements it neither composes nor writes, including the error announcements about root paths it supplied itself. The package holds two files, and the division between them is what makes the binary testable.
  • entry.py defines main(argv: list[str]) -> int, the skip list, and the extension point.
  • __main__.py holds three lines - the import, the call, and sys.exit(main(sys.argv)) - and nothing else, so that main is a function a suite can call with an argument list of its own.
 The whole of argv is passed, element 0 included. Spec_Python_TextFinder_Cmdline.md §5 fixes that the parser skips it, so the offset is stated once and this binary does not slice the list. It reads the list's length for the bare-command-line test of Section 2 and inspects no element of it.

2.  The Startup Sequence

Spec_Python_TextFinder_Entry.md §4 fixes nine steps in order. Every return above step 7 precedes traversal, which is what §3.6 requires of a run that writes no summary.
  1. Parse. Invoke parse(argv). When it returns a ParseFailure, write that failure's diagnostic to stderr unaltered and return 1. The test is isinstance(result, ParseFailure), which is what narrows the union for a type checker. A malformed /r is not detected here; step 6 reaches it.
  2. Construct the sink. On RuntimeError or OSError, write cannot initialize output to stderr and return 2. Every later write to stdout passes through this object, so it is constructed before any of them.
  3. /H true writes help_text() through the sink with write_text, returns 0, and does not proceed.
  4. The bare command line. If argv holds one element, write options_text(commands) through the sink, return 0, and do not proceed. This is §3.1, and it succeeds: nothing was asked for and nothing failed.
  5. /v true writes the same listing before traversal begins. Steps 4 and 5 are mutually exclusive: a command line bearing /v holds more than one element.
  6. Finalize the skip list and construct the Dirnav, passing the sink, that list as a tuple, and the parsed commands. Expression compilation occurs here. Section 4 covers what happens when it fails.
  7. Traverse. For each root path, in the order /P gave them, invoke search on the same Dirnav. No root-path outcome affects the exit code.
  8. The run summary. Call emit_run_summary once, after the last root path returns. The binary supplies no count and composes no text; its whole part is knowing that step 7 is finished, which nothing inside the library can know.
  9. Return 0.
 The test at step 4 is len(argv) == 1 and not len(argv) == 0. sys.argv carries the program name in element 0 - the path of __main__.py under python -m - so a one-element list is the bare command line, as it is in C++ and Rust and is not in C#, whose string[] args holds the arguments alone. Invocation 1 of the demonstration is that case, and its /v line reads false because the listing reports an option set in which /v was never set. There is no argument-decoding step before step 1. The interpreter decodes the command line and builds sys.argv - on POSIX with the filesystem encoding and the surrogateescape error handler, on Windows from the wide API - so the argument collection and decode the Rust implementation performs, and the exit code it reserves for a failure there, have no counterpart. The specification records that as a stated property rather than an omission. Two things follow, and the specification names both. Every command line the shell can express reaches the parser, so this implementation accepts root paths and expressions the C++ implementation cannot carry through its narrow argv. And an argument the interpreter could not decode carries lone surrogates into the option listing, where Spec_Python_TextFinder_Output.md §5 fixes what the sink writes for them; a root path carrying them draws cannot open. Every exit above is a return from main. sys.exit is not called inside main and os._exit is not called anywhere. The first would express a return value as an exception, which a suite calling main would then have to catch; the second terminates the process immediately, with the sink's buffer unwritten. Only a return leaves the with statement and releases the sink, which flushes its stdout buffer. sys.exit appears once in this component, in __main__.py, where it converts the returned value into the process's exit code after the with statement has already ended.

3.  Why the Construction Sits Outside the with

Step 2 splits what a Python reader would write as one statement. The sink is constructed inside a try block and then held by a with statement covering the rest of main: 
try:
    sink = StdoutSink()
except (RuntimeError, OSError):
    _write_stderr("cannot initialize output\n")
    return 2

with sink:
    ...
Writing with StdoutSink() as sink: would put the construction inside the statement, where an except clause covering the body would also cover the body's own failures. Splitting the two is what lets the construction failure be handled alone and the flush still be guaranteed. Each implementation reaches the same split with the construct its language offers. C++ uses a std::optional so the sink can be built in a guarded scope and outlive it; C# splits a try from a using statement; Python splits a try from a with. The three look unlike one another and answer the same question: a failure in constructing the sink is not a failure of the run the sink would have carried. The two exception types are the ones Spec_Python_TextFinder_Output.md §4 names. RuntimeError is the one-sink rule refusing a second sink; OSError is a process started with no usable standard output handle. Exit code 2 is reachable in this implementation, and the one-sink rule is what makes it so - this binary constructs exactly one sink, so its own code cannot provoke the first, and it handles the case because a constructor with a failure mode callers ignore is a constructor whose failure mode will eventually be reached.

4.  The Malformed Expression

The Dirnav constructor compiles the /r expression and raises re.error when it will not compile. That is the seventh usage condition of §5.2, and the binary is what writes it. Four things happen in order:
  1. If step 5 did not already write it, write the option listing now, so that the user sees the /r line carrying the expression that failed. §5.2 requires this listing whatever /v says, and §5.3 requires it not be repeated when /v already produced it.
  2. Call flush on the sink, so that the listing reaches the stream ahead of the diagnostic that explains it. The sink buffers stdout without per-line flushing, so without this the two arrive out of order.
  3. Compose the usage diagnostic in the shape §5.2 binds - the reason line invalid regex for switch: /r, a newline, then usage_line() - and write it to stderr.
  4. Return 1, having traversed nothing.
 The binary composes that diagnostic; neither python_textfinder_cmdline nor python_textfinder_dirnav does, the former supplying only usage_line() and the latter only the failure that triggers it. Spec_Python_TextFinder_Entry.md §6 fixes the reason line for this implementation, since the binary is what writes it. The message re.error carries is not written, for a reason that outlives §5.2's wording: that text is the interpreter's, so an interpreter upgrade would change this program's output without any document in this tree recording the change. What the user gets instead is the /r line above, carrying the expression as typed. The integration suite asserts that stderr holds exactly two lines here, which is the check that would fail if the interpreter's text ever reached it. re.error is caught by its own type rather than as Exception or as ValueError, which it derives from. A broader except would also swallow an argument defect in this binary's own call and report it as a malformed user pattern. Invocation 10 of the demonstration is this path end to end: nine listing lines on stdout, two diagnostic lines on stderr, exit 1, and no file read - the expression is built before the first root path is visited, so a bad pattern costs no traversal.

5.  The Skip List

python_textfinder_entry owns the process-wide skip list, initialized with the eleven defaults §3.2 fixes: 
archive, .git, .svn, .hg, build, out, target, bin, obj, __pycache__, node_modules
The module holds the list at module level and implements the build-time extension point of §3.5: 
_SKIP_LIST: list[str] = [ ... the eleven defaults ... ]

def _add_skip_directory(name: str) -> None: ...
_add_skip_directory takes the name alone, as §3.5 writes it, and returns None. §3.5 fixes the shape and leaves the spelling to each language, so the name is snake_case here where §3.5 writes addSkipDirectory. It ignores a name the list already holds, comparing with the same platform rule python_textfinder_dirnav applies to a skip-list entry, so a build that adds Build on Windows does not lengthen a list that already holds build. The calls that extend the list are written into this module, beneath the list's definition, and run when the module is imported - before main is called and therefore before traversal begins. A list needs no interior-mutability type and no synchronization primitive to be extended from a module-level function, so the RefCell and thread_local! pair the Rust implementation requires has no counterpart. Both names carry a leading underscore, which is the whole of Python's access control. Nothing prevents another module from importing and calling _add_skip_directory, where the C# implementation's private and the C++ implementation's internal linkage prevent it outright. The specification records that as a stated weakness of this implementation rather than a difference in design, and the rule it rests on is that no library and no suite in this project calls either name. The list is handed to the Dirnav as a tuple. That library can read it and cannot modify it - a stronger guarantee than the C# implementation's IReadOnlyList<string>, through which a caller holding the underlying list can still change what the library sees. The two facts in this section run in opposite directions, and the specification states both rather than picking the flattering one: Python gives the weaker guarantee at the module boundary and the stronger one at the call. Nothing extends the list once traversal has begun, and the binary reads no configuration file and offers no runtime means of extending it. Invocation 8 of the demonstration shows the default list doing its work: __pycache__ sits beneath both roots and contributes nothing to the counts.

6.  Exit Codes and Diagnostics

The three codes §3.4 fixes map onto this binary's failure modes as follows. No other value is returned from main.
Code Condition
0 All startup steps and traversal completed; or /H true printed help; or the command line was bare. Match count and unopenable root paths do not affect it.
1 Parsing failed, or /r was a malformed expression. Both are usage diagnostics, in the shape §5.2 binds.
2 Constructing the StdoutSink failed. Neither cause writes a usage line, since neither is a usage diagnostic. The text is cannot initialize output.
Only one exit-code-1 path writes to stdout: the malformed expression, whose option listing Section 4 requires. A parse failure leaves stdout empty, as does the code-2 failure, which occurs before the sink exists or because it does not. An uncaught exception escaping main is not one of the three codes. The interpreter would print a traceback to stderr and exit 1, which would be read as a usage failure and would carry no usage line. Nothing in this binary is written to allow that: python_textfinder_dirnav contains every OSError it meets and python_textfinder_output contains every write failure, so the two exception types that reach this module are the ones steps 2 and 6 name. The integration suite asserts that no traceback reaches stderr on any of six command lines. The one uncontained case is the RecursionError a tree deeper than the interpreter's limit would raise, which the Dirnav specification leaves uncontained deliberately and which would exit this way. It is named here rather than left as the one exception to an otherwise unconditional claim.

7.  Writing to stderr

Every stderr write in this binary goes to sys.stderr.buffer as UTF-8 with an explicit \n, followed by a flush. sys.stderr.write is not used: it writes through a text layer opened with newline=None, which translates to CRLF on Windows. §3.4 leaves the stderr terminator to the platform and would permit CRLF here. Writing LF costs one writer choice and makes this implementation's stderr identical on both platforms, so it is fixed in the specification rather than left to the runtime. The integration suite asserts it at the byte level, through a pipe, on Windows. Every stderr write is wrapped against OSError and ValueError and its failure discarded, for the reason the Output specification gives for the sink's own notice: a process whose stderr is broken must still return the code Section 6 assigns, and an exception raised while reporting a usage error would replace that code with an interpreter traceback and a 1 that means something else. A run that cannot say why it failed still fails with the right number. The encode uses errors="replace". A reason line may reproduce a token the interpreter decoded with surrogateescape, and a diagnostic that raised while reporting a bad command line would be worse than one that renders a byte as ?. Nothing in this implementation writes through sys.stdout, so the interpreter's own flush of that stream at shutdown has nothing to write and can fail at nothing. That is why a broken pipe produces the sink's one output failed notice and not, in addition, the interpreter's shutdown complaint about an unflushable stdout. Nothing writes to stderr before stdout has been flushed. Step 1 predates the sink and so has no buffer to flush; step 2 fails before one exists; step 6 flushes explicitly.

8.  Build and Launch

There is no build step and no project file. Python compiles on import, so this component is run as python -m python_textfinder_entry once the four src/ folders are on PYTHONPATH. The launchers Python_TextFinder.bat and Python_TextFinder set that path, forward their arguments, and return the interpreter's exit code unchanged. Python_TextFinder is the name §5.1 substitutes for <executable>, and that substitution is fixed in python_textfinder_cmdline rather than read from sys.argv[0], which under python -m holds a path. The binary imports the three libraries and os, re, and sys from the standard library. os is imported for os.name alone, which Section 5 needs to compare a skip-list name by the platform rule the Dirnav specification fixes; that rule is two lines and is written out here rather than reached for through another package's private name. That import was missing from the specification's own build list until turn 2, which corrected the document before writing the code. No locale is read. This implementation calls locale.setlocale nowhere, opens no stream it did not configure, and performs no culture-sensitive comparison, so no locale data can change what it does. The InvariantGlobalization switch the C# implementation sets has nothing here to switch off.

9.  Source

entry.py in full, at 87 lines. The nine steps of Section 2 are the body of main in order, and the two module-level helpers above it are the skip list's comparison and the extension point.
Python_Spec_driven_TextFinder_Entry/src/python_textfinder_entry/entry.py
# entry.py - startup sequence, skip-list ownership, and exit codes

import os
import re
import sys

from python_textfinder_cmdline import (ParseFailure, help_text, options_text,
                                       parse, usage_line)
from python_textfinder_dirnav import Dirnav
from python_textfinder_output import StdoutSink

_WINDOWS = os.name == "nt"

_SKIP_LIST: list[str] = [
    "archive",
    ".git",
    ".svn",
    ".hg",
    "build",
    "out",
    "target",
    "bin",
    "obj",
    "__pycache__",
    "node_modules",
]


def _names_equal(left: str, right: str) -> bool:
    if _WINDOWS:
        return left.lower() == right.lower()
    return left == right


def _add_skip_directory(name: str) -> None:
    for existing in _SKIP_LIST:
        if _names_equal(existing, name):
            return
    _SKIP_LIST.append(name)


def main(argv: list[str]) -> int:
    result = parse(argv)
    if isinstance(result, ParseFailure):
        _write_stderr(result.diagnostic)
        return 1
    commands = result

    try:
        sink = StdoutSink()
    except (RuntimeError, OSError):
        _write_stderr("cannot initialize output\n")
        return 2

    with sink:
        if commands.help:
            sink.write_text(help_text())
            return 0

        if len(argv) == 1:
            sink.write_text(options_text(commands))
            return 0

        if commands.verbose:
            sink.write_text(options_text(commands))

        try:
            dirnav = Dirnav(sink, tuple(_SKIP_LIST), commands)
        except re.error:
            if not commands.verbose:
                sink.write_text(options_text(commands))
            sink.flush()
            _write_stderr("invalid regex for switch: /r\n" + usage_line())
            return 1

        for root in commands.root_paths:
            dirnav.search(root)
        dirnav.emit_run_summary()
        return 0


def _write_stderr(text: str) -> None:
    try:
        sys.stderr.buffer.write(text.encode("utf-8", "replace"))
        sys.stderr.buffer.flush()
    except (OSError, ValueError):
        pass
_names_equal is duplicated between this module and python_textfinder_dirnav, and the duplication is deliberate. The rule is two lines, and the alternative is this binary importing a private name from a library it is meant to depend on only through its public interface. Both copies implement the one comparison §3.2 and §5 fix, so a change to the rule is a change to the parent and then to two files. tuple(_SKIP_LIST) is built at the point of the call rather than held as a constant, so the extension calls that ran at import are already in it and nothing after it can be. That one expression is the whole of the handoff guarantee Section 5 describes.
Python_Spec_driven_TextFinder_Entry/src/python_textfinder_entry/__main__.py
# __main__.py - converts main's returned value into the process exit code

import sys

from .entry import main

sys.exit(main(sys.argv))
Three lines, and the placement of the one sys.exit is the point: it runs after main has returned, so the with statement has already released the sink and flushed the buffer. Every suite in this implementation calls the program as a subprocess rather than calling main directly, but the split is what would let one do either.
